# OFA 有、本 Demo 没做的部件清单

目的：把"这个实践离 OFA（arXiv:1908.09791）还差什么"一次说清，避免被误读成"OFA 的实现"。
状态只用三种：**已实现** / **可选实现** / **未实现**；最后附"要补的话按什么顺序补"。

> 本文只做**部件层面**的对照。凡是涉及 OFA 论文里的具体数值（epoch 数、ImageNet 精度、延迟），
> 一律没有引用——需要的话请查原文，不要拿本文档当出处。

---

## 一、部件对照表

| OFA 的部件 | 本仓库状态 | 说明 |
| --- | --- | --- |
| 弹性宽度（width multiplier） | **已实现** | `embed_dim` 取前 d 个通道切片，子网天然可用 |
| 弹性深度 | **已实现** | 截断：depth L 只跑前 L 层 |
| 弹性卷积核（3/5/7 → 本仓库 1/3/5） | **已实现** | 靠**并列分支**而非切片；实测切片替代方案会掉 10 个点（95.31 → 84.96） |
| 弹性扩展比（expand ratio） | **已实现** | `ffn_ratio` 2/3/4，同样是分支选择 |
| 弹性 head 尺寸 | **额外实现** | OFA 没有这一维；我们让 head 数随宽度自动变化 |
| 三明治规则（max + min + n random） | **已实现** | 默认 n_random=2，四条腿求和后一次 optimizer step |
| in-place distillation（大子网教小子网） | **已实现但简化** | `--distill-weight` 默认 0.5；**未做**蒸馏温度、未做 teacher 的 EMA/更新策略（teacher 就是同一步的 max 腿） |
| 渐进收缩（progressive shrinking） | **简化版可选** | `--shrink-stages 4`：等长阶段、深度/宽度/核**同时**解锁；OFA 是按维度分阶段、每段训到收敛 |
| BN 重估（BN re-estimation） | **不需要** | 本仓库用 LayerNorm（无 running 统计），导出子网即用；换成 BN 就必须重估 |
| 导出子网微调（specialization） | **已实现** | `rank.fine_tune_subnet()`，报告 §3 有实测表 |
| 按设备专化（每个硬件一个专化模型） | **未实现** | 我们只有一个目标（MNIST 精度），没有"设备"这一维 |
| 弹性分辨率（resolution） | **未实现** | 输入固定 28×28，搜索空间里没有 resolution 维度 |
| 真实延迟/FLOPs 目标 | **未实现** | 只有**参数量**代理；不测延迟、不查表、无硬件在环 |
| 搜索算法（进化搜索 + 延迟约束） | **未实现** | 我们只做"评估器"，不做"搜索器"；候选是随机采样与固定角点 |
| 训练设施：LR schedule | **未实现** | 恒定 lr=3e-3 的 AdamW |
| 训练设施：数据增强 / dropout / label smoothing | **未实现** | 一律没有 |
| 训练设施：AMP / 多卡 DDP / EMA | **未实现** | 单设备 float32 |
| 训练规模 | **差距很大** | 本仓库 1058 步 ≈ 2.3 个 MNIST epoch，单机几分钟；OFA 是 ImageNet 级别的多阶段训练 |

## 二、这些"没做"各自意味着什么

| 缺的部件 | 直接后果 | 补的话要动哪里 |
| --- | --- | --- |
| 弹性分辨率 | 少了一整条"用分辨率换延迟"的曲线，这是移动端部署最常用的一维 | `tasks.py`（可变窗口）+ `supernet.py`（位置编码按长度切） |
| 真实延迟目标 | 第 5 节的"成本"是参数量，**不能**当 ms 用；Pareto 前沿无法对齐真实硬件 | 加一个延迟测量/查表模块，替换 `subnet_parameter_count` 的成本列 |
| 搜索算法 | 本仓库能回答"这些子网谁好"，但**不能**回答"最优子网是哪个" | 在 `rank.py` 之上加进化/贝叶斯搜索，成本函数用延迟 + 精度 |
| 按设备专化 | 只有一份"通用"子网，没有"某设备专用"子网 | 需要设备维（多个延迟表）+ 每设备一份 fine-tune |
| 蒸馏的完整细节 | 现在 λ 固定 0.5、无温度、无 teacher 平滑；教师欠训时会把错误传下去 | `losses.distillation_loss` 加温度参数，`sandwich.leg_loss` 加调度 |
| 渐进收缩的完整排程 | 我们的等长阶段在同一小预算下**反而更差**（min 子网 96.2% → 78.0%），因为解锁太晚 | `shrink.py` 改成按维度分阶段 + 每段训到收敛 |
| 训练设施（schedule/增强/AMP/DDP） | 精度上限被压低，也无法在 ImageNet 规模上跑 | `sandwich.py` 加 scheduler、`dataset.py` 加增强、加 AMP/DDP 封装 |
| 训练规模 | 所有数字都是"小规模下的趋势"，不是"能达到的最好结果" | 纯算力问题 |

## 三、我们反而**多做**的（OFA 不报的东西）

| 我们做的 | 为什么值得 |
| --- | --- |
| **排序审计**（τ / ρ / recall@k / regret） | 直接量出"超网内分数能不能用来筛选"，本仓库实测 τ≈0.24、recall@3 = 2/3 |
| **切片示意图由 spec 驱动** | 图和具体架构严格对应，不用手绘占位 |
| **arch_id 记账口径** | 明确"只哈希可搜索变量"，写清改固定结构时 arch_id 不变的坑 |
| **预算自适应规划** | 按墙钟预算反推步数，慢机器也能在 5 分钟内出结果 |
| **参数分解（`parameter_breakdown`）** | 解释"超网 18.42M vs max 子网 4.61M"的差额从哪来（每层 8 条未用分支） |
| **可复现性** | 固定 `--steps` + `--seed` 时三次运行结果逐位一致；`metrics.json` 记录 git commit / torch / python / platform |

## 四、如果要补齐，按性价比排序

| 优先级 | 补什么 | 工作量 | 收益 |
| --- | --- | --- | --- |
| 1 | 蒸馏的完整细节（温度 + 调度） | 小（~30 行） | 直接改善低端子网，默认已开 |
| 2 | 真实延迟测量（单设备） | 中（~80 行 + 一次测量） | 把"成本"从参数量换成 ms，Pareto 才有意义 |
| 3 | 搜索算法（进化 + 延迟约束） | 中（~150 行） | 从"评估器"变成"搜索器" |
| 4 | 弹性分辨率 | 中（改 token 化 + 位置编码） | 多一维成本控制 |
| 5 | 训练设施（schedule/增强/AMP） | 小到中 | 抬高精度上限 |
| 6 | 按设备专化 + 多延迟表 | 大 | 真正的部署场景 |
| 7 | ImageNet 规模训练 | 很大（算力） | 可与论文横向比 |

## 五、边界声明

- 本仓库的定位是**可复现的最小超网实践**：一次训练得到一个子网族，并把失效场景量出来；
  它**不是** OFA 的复现，也不追求在其指标上可比。
- 上面所有"未实现"都不影响本仓库已有的结论（切片近似、覆盖分布、排序不可靠、蒸馏便宜且有效），
  因为这些结论都是在**同一套受控条件**下测出来的。
- 若要把本仓库数字与任何论文数字并列，必须先对齐：数据集、训练预算、评估器口径（`evaluator_kind`）。

## 六、补充：OFA 侧的具体数值（论文附录 B 原文）

> 上面第一节刻意"不引用论文数值"。若确实需要与论文对齐，这一节是唯一的出处；
> 数字直接取自 arXiv:1908.09791 附录 B *Implementation Details of Progressive Shrinking*。

渐进收缩（PS）在 ImageNet 上的完整流程——先训完整网络，然后依次做 5 段微调：

| # | 解锁什么 | 取值 | epochs | 初始 lr | 每步采样子网数 |
| --- | --- | --- | --- | --- | --- |
| 0 | 完整网络（不可弹） | — | — | — | — |
| 1 | **kernel size** | K ∈ [7, 5, 3] | 125 | 0.96 | 1 |
| 2 | **depth**（第一段） | D ∈ [4, 3] | 25 | 0.08 | 2 |
| 3 | **depth**（第二段） | D ∈ [4, 3, 2] | 125 | 0.24 | 2 |
| 4 | **width**（第一段） | W ∈ [6, 4] | 25 | 0.08 | 4 |
| 5 | **width**（第二段） | W ∈ [6, 4, 3] | 125 | 0.24 | 4 |

合计 **425 个 epoch** 的渐进微调。三个关键设计点，都与本仓库的实现不同：

1. **一次只放开一个维度**（kernel → depth → width），不是同时放开；
2. **每段都训到收敛再解锁下一段**，并且**重置学习率**（0.96 / 0.08 / 0.24 各段不同）；
3. **每步采样子网数随阶段变化**（1 → 2 → 4），不是固定四条腿。

对照本仓库的 `--shrink-stages N`：等长分段、所有维度同时放开、lr 全程不变、腿数固定。
本仓库一次运行约 2.5 个 MNIST epoch，PS 开启时每段约 0.6 epoch —— 与"每段 25–125 epoch"差两个量级，
这就是 PS 在本仓库反而更差的直接原因（见 `docs/comparison.md`）。

### 其他机制的名称与出处（便于查原文时定位）

| 机制 | 论文里的说法 | 本仓库 |
| --- | --- | --- |
| 弹性卷积核如何共享权重 | **kernel transformation matrix**（用小变换矩阵把中心核映射成 3/5/7） | 9 条独立分支，不共享核 |
| 弹性宽度如何初始化 | **channel sorting**（按 L1 重要性挑通道，初始化更小的宽度设置） | 直接取前 d 个通道切片 |
| 精度代理 | **accuracy predictor**（架构 + 分辨率 → 精度），训练于采样子网 | 无（直接实测候选） |
| 延迟代理 | **latency lookup table**（逐算子测量） | 无（只有参数量代理） |
| 部署搜索 | 进化搜索 + 延迟约束，用上面两个 predictor | 无（只做评估与审计） |

> **BN 重估（BN re-estimation）流程**出自 OFA 代码库与后续工作（如 BigNAS），并非该论文正文措辞，
> 引用时不要归到论文头上。
